demo-environment — the intended flows

Four views of the unified demo-build skill as specced on the feat/demo-environment branch: how a run picks its path, the phase skeleton with its two gates, the Shopify order engine, and the default order set with the comm story each order tells.

Engage Retain · non-Shopify Retain · Shopify delay / problem

1 · Which path a run takes

Two intake questions route everything. Retain covers the Engage story automatically (its orders still fire every tracking comm), so there is no separate "both" pipeline — and an Engage-only run never asks about Shopify.

2 · The run skeleton — phases, gates, concurrency

All three paths share this skeleton. Two things pause a run: the ✋ approval gate at the end of intake and the ★ template checkpoint — the only mid-run moment that needs you. Everything below the publish gate runs unattended.

3 · The Shopify order engine — one order's journey

Repeated per order (3 by default, up to 5). Solid arrows are the skill acting; dashed arrows are the installed parcelLab Shopify app doing its real job — which is the point: the demo runs on the genuine integration.

4 · The default order set — events and comm arcs

"Give me the default 3" produces one order per comm arc: clean, stuck, and delayed-but-recovered. Event names are the literal event_status values pushed; ✉ marks the comm each event is expected to fire. Fraud level rides on every order and maps one-to-one onto the CDC's fraud slots.
